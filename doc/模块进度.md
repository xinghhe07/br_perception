## 三、一步一轮：每轮固定 6 步

1. **抽规格** → 从任务书对应章节 + 相关 msg/yaml 抽出**自包含规格**（实现不靠猜）
2. **先写 .hpp，冻结契约**（参数名 = yaml 键名 = `Params` 字段名，三方逐字一致）
3. **写 .cpp**
4. **对抗复核**：全新上下文的 agent，"默认有错"，专找编译失败与规格不符

### ⚠ 2026-09-19 新增的两个缺口（别只留在对话里）

**① 通信层没有"下发速度"的通道 —— 由"决策上主机"带来，不是跑点带来的。**

`comm_node` 现在只有一个上行入口：订阅 `/perception/output` → 编码 → 串口；
`PacketType` 只有 `PERCEPTION=0x01` / `HEARTBEAT=0x02`，**没有任何一种能携带速度指令**。
决策改到主机后（任务书 §十 1），主机必须能把运动指令发给 STM32：

- 新增 `PacketType::CMD_VEL`（编号与下位机商定）
- `comm_node` 加订阅 → 编码 → 入队
- 帧格式（`linear_x/y/angular_z`，f32 还是定标 int16）+ **频率** → 并入第 4 项「协议冻结」，**与下位机一起定**

⚠ 方向是**上行**（主机→主控），**与感知帧共用同一条 115200 预算** —— 9-19 实测满载荷上限 **41 fps**。
✅ 下行反而变轻："目标点 / 期望路径下发"作废，`protocol_decoder` 不用长大。

**② 雷达层有 4 个孤儿话题（发了没人订阅）**

`/perception/lidar/{l0,l1,l2}_surface` + `/perception/lidar/ground_plane` —— `ground_segmenter`
**每帧发三份 PointCloud2**，而全仓库**零订阅者**（launch / RViz / 代码都没有）。
它们是为"分层 costmap"准备的**逐层地面点云**，该方案已于 2026-09-19 移出主线

**处置：现在不删** —— 它们已写进容器化重构任务 4 的**接口定义与验收判据**

### ⚡ 长跑 + 满载荷压力测试（2026-09-19，约 25 分钟 / 4 万帧）

**为什么要做**：波特率是 4 项未冻结协议参数之一，而"够不够"只能靠实测。
载荷取单帧上界 = 16 建筑位 + 10 障碍物 → payload 272 B、**线上 280 B**
（26 + (1+4×16) + (1+18×10) = 272，+6 帧头 +2 CRC）。

**关键方法坑：socat 的 PTY 不模拟波特率。** 纯 PTY 下 100 Hz 满载荷（28 kB/s）
照样零丢弃 —— 字节是内存速度传的。要测物理层必须自己按 `baud/10` 限速转发。
本次为此写了一个令牌桶中继（comm_node → 中继 → 伪下位机），并且**令牌桶必须带容量上限**：
第一版用"允许 = 速率×已过时间 − 已发"的累计式，空闲期把额度攒起来、洪峰时一次透支，
实测瞬时冲到 13.9 kB/s **突破了 11520 的上限，等于没限速**。

#### 结果一：性能上限（理论 vs 实测）

| 相位 | 发布 | 串口发出 | 丢于投递 | 丢于发送 | 实际到端 | 平均陈旧度 |
|---|---|---|---|---|---|---|
| 10 Hz × 180s（无限速） | 1800 | 1800 | 0 | 0 | 1800 | ~2 ms |
| 50 Hz × 120s（无限速） | 6000 | 6000 | 0 | 0 | 6000 | ~2 ms |
| 100 Hz × 60s（无限速） | 6000 | 6000 | 0 | 0 | 6000 | ~2 ms |
| 10 Hz × 60s @115200 | 600 | 590* | 0 | 0 | 590 | ~2 ms |
| 30 Hz × 60s @115200 | 1800 | 1800 | 0 | 0 | 1800 | ~2 ms |
| 50 Hz × 90s @115200 | 4485 | 3752 | 643 | 58 | **3752 = 41.7 fps** | **1.7 s** |
| 100 Hz × 60s @115200 | 6000 | 2561 | 3386 | 53 | **2561 = 42.7 fps** | **1.7 s** |
| 50 Hz × 300s @115200 | 15000 | 12400 | 2331 | 235 | **12400 = 41.3 fps** | **1.755 s** |

\* 这 590 不是链路丢帧 —— 见下面"测试工件"一节。

**满载荷吞吐上限：理论 11520 B/s ÷ 280 B = 41.1 fps，三个独立相位实测 41.7 / 42.7 / 41.3 —— 吻合。**

#### 结果二：超容量时的降级行为（★ 本轮最重要的发现）

超过链路容量时系统**不是**"降级到较低频率"，而是**丢帧 + 叠加约 1.75 秒延迟**，
且**延迟在 comm_node 的诊断里完全不可见**（那里只看到 `frames_dropped_on_post` 在涨）。

- 延迟稳态：平均 1.70 → 1.755 s，最大 2.74 s，**5 分钟不增长**（有界，非累积）
- 1.755 s × 11520 B/s ≈ **20 kB 的下游缓冲** = socat 内部 8 kB + 两端 PTY 缓冲
- ⚠ 真实 UART 没有 socat 那 8 kB，内核 tty 缓冲通常 4 kB 量级 → 现场陈旧度应更小，
  但**机制相同**（缓冲吃满 → 数据出生即过期），且量级仍需现场实测
- 对控制的影响：3 m/s 行进时 1.75 s = 5 m 位置误差，即"按 1.75 秒前的位置避障"

**推论（要写进协议冻结）**：发布侧必须限频，且限频阈值要按**满载荷 41 fps** 反推并留余量。
满载荷下 115200 只够 41 fps；想跑 50 Hz 需要 230400（82 fps）或更高。

#### ⚠️ `config/comm_params.yaml` 里有一条算错的注释（**待 Windows 侧修**）

`max_building_spots` / `max_obstacles` 上方那段注释写：

> "115200 bps 下 200 字节约 17ms —— 想同时保持 send_rate_hz=50 不拥塞,
>  **建议 N ≤ 32, M ≤ 20**。当前 16/10 是任务书给的保守值, 别随手调大。"

**按同一套算法代入 N=32、M=20**：

```
payload = 26 + (1 + 4×32) + (1 + 18×20) = 26 + 129 + 361 = 516 B
线上    = 516 + 8                                        = 524 B
115200 下耗时 = 524 ÷ 11520                             = 45.5 ms
→ 上限    = 1 ÷ 0.0455                                   = 22 Hz
```

**22 Hz ≠ 50 Hz，差了约 2 倍。** 这句注释会被人当真（"任务书给的保守值，别随手调大"
很容易被读成"调到 32/20 也没事"），实际调上去直接掉到 22 Hz。
建议改成按实测反推的写法，例如：

> 单帧线上字节 = 36 + 4N + 18M；115200 下可持续帧率 = 11520 ÷ (36 + 4N + 18M)。
> 当前 16/10 → 280 B → **41 fps**（2026-09-19 实测 41.3 fps，吻合）。
> 发布侧频率必须低于此值，否则丢帧**且**叠加约 1.7 s 陈旧度（见上）。

### 台架状态坑（2026-09-18 VM 实测，别再误判）

**socat 跑着的时候 kill 掉 comm_node，会导致 socat 往 master 写的那一端坏掉、且 socat 进程不退出。**
症状：伪下位机收不到新数据（`bytes` 不涨），看起来像代码坏了。
处理：**整套重起**（socat + comm_node + fake_master），与代码无关。
