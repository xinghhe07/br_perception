## 零、★ 第一宗旨（2026-09-23 立，**一切改动排在它之后**）

> **为了比赛成绩，追求「快、准、稳」。**
>
> 这是个 **180 秒的比赛**，不是软件工程项目。
> **文件整齐、注释完备、工具漂亮都不直接得分** —— 机器人在那 3 分钟里多建一座塔、
> 少撞一次、少停一次，才得分。

**每个改动动手前先问一句**：

> 「这能让机器人在 180 秒里**多拿分**吗，还是只是让文件更整齐？」

答不上"多拿分"的**可以做**（卫生工作该做，它防的是"将来某天静默失效"），
但**必须明说它是卫生工作、排在后面**，别当成进展汇报。
⚠️ 汇报时**按比赛影响排序**，不要按"改了哪些文件"排序。

| 轴 | 具体是什么 | 反面（本仓库踩过的） |
|---|---|---|
| **快** | 延迟就是分数：端到端预算 §15.3（warn 56ms / error 80ms），雷达 34ms、视觉 46ms。多出的每毫秒都变成"按旧位置动作"。**开发速度也算快** —— 能 3 行解决的别写 30 行 | 为了"结构更漂亮"推迟能让系统跑起来的事 |
| **准** | 送到主控的**每个数都必须是"真的"**：坐标真在 `header.frame_id` 声明的那个系里；"未知"要有**协议定义的哨兵**，**不许用 0 冒充** | 零值 `PoseStamped` = "西南角那个点"（不是"没填"）；`sanctuary=0` = "使命未达成" → TR 白丢 250 分 |
| **稳** | **不能静默失效**；某一路死了要如实降级并**点名**，不能拖垮别的路 | yaml 键与 `declare_parameter` 对不上 / QoS 不匹配 / 话题名错 / **同名键靠 launch 顺序定值** / 节点名与参数块名不一致 —— 症状全是"**看着配好了，实际没接上**"，bench 能跑、比赛翻车 |

**自动核对**：`python3 scripts/check_param_consumers.py`（查的就是"稳"里的静默失效那一类）。

**配套约定 —— 提交与真机测试的节奏**（2026-09-22 用户定）：
- **不逐轮提交**：本机无 ROS，写出来的 C++ 一行都编译不了，单独提交没有验证价值；
  攒到"要接相机/雷达内外参"时**总提交**。
- 但**必须真机测**的时候要主动说 —— 具体是：改了通信层（🟢 测过的模块）、
  动了 QoS/话题名/定时器这类只有跑起来才知道对不对的东西、
  或**再往下做就会把错误叠加起来**的时候。
- ⚠️ **"提交"与"上真机"是两件事**：`colcon build` **不需要内外参**
  （那是运行期的值）。所以"为了编译一次"而提交是成立的，不必等标定。

> ⚠️ 这条宗旨**不否定一切**：卫生工作（去重、文档、工具）该做。
> 要求只是**分清它是什么**，别把洁癖当战果。

### ⚠ 2026-09-19 新增的两个缺口（别只留在对话里）

**① 通信层没有"下发速度"的通道 —— 由"决策上主机"带来，不是跑点带来的。**

`comm_node` 现在只有一个上行入口：订阅 `/perception/output` → 编码 → 串口；
`PacketType` 只有 `PERCEPTION=0x01` / `HEARTBEAT=0x02`，**没有任何一种能携带速度指令**。
决策改到主机后（任务书 §十 1），主机必须能把运动指令发给 STM32：

- 新增 `PacketType::CMD_VEL`（编号与下位机商定）
- `comm_node` 加订阅 → 编码 → 入队
- 帧格式（`linear_x/y/angular_z`，f32 还是定标 int16）+ **频率** → 并入第 4 项「协议冻结」，**与下位机一起定**

⚠ 方向是**上行**（主机→主控），**与感知帧共用同一条串口预算** ——
9-19 在 **115200** 下实测满载荷上限 **41 fps**；但波特率 **2026-09-20 已提到 460800**
（`config/comm_params.yaml:58` + `serial_manager.hpp:62` 两处默认值都是 460800），
按同一套算法 **460800 ÷ 10 ÷ 280 B = 164.6 Hz**，对 `send_rate_hz: 50` 有约 3.3× 余量。
✅ 下行反而变轻："目标点 / 期望路径下发"作废，`protocol_decoder` 不用长大。

**② 雷达层有 4 个孤儿话题（发了没人订阅）**

`/perception/lidar/{l0,l1,l2}_surface` + `/perception/lidar/ground_plane` —— `ground_segmenter`
**每帧发三份 PointCloud2**，而全仓库**零订阅者**（launch / RViz / 代码都没有）。
它们是为"分层 costmap"准备的**逐层地面点云**，该方案已于 2026-09-19 移出主线
（见 `doc/自主探索_多层costmap与在线规划.md`）。

**处置：现在不删** —— 它们已写进容器化重构任务 4 的**接口定义与验收判据**
（`doc/容器化重构_任务清单_20260914.md:210` 与 `:215`），现在删会让并行轨验收对不上。
→ **在容器化重构任务 4 里一并决定**（那时 `ground_segmenter` 内部本来就要重做）。

### ⚡ 长跑 + 满载荷压力测试（2026-09-19，约 25 分钟 / 4 万帧）

**为什么要做**：波特率是 4 项未冻结协议参数之一，而"够不够"只能靠实测。
载荷取单帧上界 = 16 建筑位 + 10 障碍物 → payload 272 B、**线上 280 B**
（26 + (1+4×16) + (1+18×10) = 272，+6 帧头 +2 CRC）。

**关键方法坑：socat 的 PTY 不模拟波特率。** 纯 PTY 下 100 Hz 满载荷（28 kB/s）
照样零丢弃 —— 字节是内存速度传的。要测物理层必须自己按 `baud/10` 限速转发。
本次为此写了一个令牌桶中继（comm_node → 中继 → 伪下位机），并且**令牌桶必须带容量上限**：
第一版用"允许 = 速率×已过时间 − 已发"的累计式，空闲期把额度攒起来、洪峰时一次透支，
实测瞬时冲到 13.9 kB/s **突破了 11520 的上限，等于没限速**。

#### 结果一：性能上限（理论 vs 实测）

| 相位 | 发布 | 串口发出 | 丢于投递 | 丢于发送 | 实际到端 | 平均陈旧度 |
|---|---|---|---|---|---|---|
| 10 Hz × 180s（无限速） | 1800 | 1800 | 0 | 0 | 1800 | ~2 ms |
| 50 Hz × 120s（无限速） | 6000 | 6000 | 0 | 0 | 6000 | ~2 ms |
| 100 Hz × 60s（无限速） | 6000 | 6000 | 0 | 0 | 6000 | ~2 ms |
| 10 Hz × 60s @115200 | 600 | 590* | 0 | 0 | 590 | ~2 ms |
| 30 Hz × 60s @115200 | 1800 | 1800 | 0 | 0 | 1800 | ~2 ms |
| 50 Hz × 90s @115200 | 4485 | 3752 | 643 | 58 | **3752 = 41.7 fps** | **1.7 s** |
| 100 Hz × 60s @115200 | 6000 | 2561 | 3386 | 53 | **2561 = 42.7 fps** | **1.7 s** |
| 50 Hz × 300s @115200 | 15000 | 12400 | 2331 | 235 | **12400 = 41.3 fps** | **1.755 s** |

\* 这 590 不是链路丢帧 —— 见下面"测试工件"一节。

**满载荷吞吐上限：理论 11520 B/s ÷ 280 B = 41.1 fps，三个独立相位实测 41.7 / 42.7 / 41.3 —— 吻合。**

#### 结果二：超容量时的降级行为（★ 本轮最重要的发现）

超过链路容量时系统**不是**"降级到较低频率"，而是**丢帧 + 叠加约 1.75 秒延迟**，
且**延迟在 comm_node 的诊断里完全不可见**（那里只看到 `frames_dropped_on_post` 在涨）。

- 延迟稳态：平均 1.70 → 1.755 s，最大 2.74 s，**5 分钟不增长**（有界，非累积）
- 1.755 s × 11520 B/s ≈ **20 kB 的下游缓冲** = socat 内部 8 kB + 两端 PTY 缓冲
- ⚠ 真实 UART 没有 socat 那 8 kB，内核 tty 缓冲通常 4 kB 量级 → 现场陈旧度应更小，
  但**机制相同**（缓冲吃满 → 数据出生即过期），且量级仍需现场实测
- 对控制的影响：3 m/s 行进时 1.75 s = 5 m 位置误差，即"按 1.75 秒前的位置避障"

**推论（要写进协议冻结）**：发布侧必须限频，且限频阈值要按**满载荷帧率**反推并留余量
（公式见下）。

1. **触发条件 = 雷达报 `state == 3 (完整塔)`**：本模块只做判色、不做检测，

3. **一帧可发多条消息**：`CameraSkyBlock.msg` 的 `spot_id` 是单数的（一条观测 = 一个目标），

### 9.4 天空方块的「红蓝怎么分布」—— **2026-09-24 已裁定：顶面是纯色**（原「红蓝各半」是误读）

**裁定依据**（用户 2026-09-24 引规则原文，不是推断）：
1. 官方定义 "colored red on one side and blue on the other" = **相对的两面**一红一蓝，
   **不是**"每一面各半";
2. 规则 3.5.6 "scored based on the color of their **top surface**" +
   3.5.8 "flip … to ensure their **color faces upward**" —— 这套判据**只有在"顶面纯色、
   翻转即换色"时才执行得了**。若顶面恒半红半蓝，**裁判自己都判不出分**，规则不可能这样写;
3. 官方总装配的"每块 = 整块 + 半块"应是**沿竖直方向**拼接的两个半部 ⇒ "红蓝各半"说的是

**（a）相机源时间戳比当前时刻早**数百毫秒**（**根因未定，但已排除两种解释**）

```

已经**排除**的两种解释（都做了实验）：

| 假设 | 判据实验 | 结果 |
|---|---|---|
| **时钟域错**（V4L2 用 MONOTONIC，转换偏移过期） | 连采样 42 s，看年龄是否漂移；同测 `realtime−monotonic` | 年龄 729~736 ms **恒定不漂**，偏移 1790308150.108 s **纹丝不动** ⇒ **排除** |

**根因未定**，要读 `usb_cam` 源码才知道它的 `header.stamp` 到底取自哪里。

预算是 warn 56 / error 80 ms ⇒ 若属实则超 **4~10 倍**。

⚠️ **顺带抓到一个 usb_cam 自己的崩溃**：`io_method:=read` **段错误**（核心已转储），
`mmap` 正常。⇒ 又一个"这个包不适合上赛场"的证据。

**结论**：`usb_cam` 是**过渡手段，不是终态**。真正的驱动应当是**本仓库自己写的 MVS 节点**
（9.14 ⑤），它能把 `header.stamp` 的来源握在自己手里 —— 而这正是现在查不清的那一环。

**`SensorDataQoS`（best-effort）**。DDS 里两者**兼容**（可靠发布端可满足尽力而为订阅端），
本次也真的跑通了 ⇒ **不是当前故障**。但大图 + RELIABLE 会**反压**，

（把 tele 误判成只有 6~15Hz，实际两路都是满帧）。**以后测帧率用消息计数，别只用 `hz`。**

**⚠️ 这一段是卫生工作，不是得分进展**：`usb_cam` 是**过渡手段**，
真正该有的是一个**本仓库自己的驱动**（见 9.14）。

#### ① ✅ Bayer 相位**已验证**（这条错了会静默判反红蓝）

⚠️ 不能用肉眼看 —— **OpenCV 的 Bayer 命名与 GenICam 的约定有已知错位陷阱**，必须实测。
方法：关掉自动白平衡，直接算 **CFA 四个平面**的均值（不经过任何 cv2 转换）：

```
两个 G 平面均值差 = 0.00                    ← 2×2 对齐正确（必要条件）
全图: (0,0)=54.4   (0,1)=51.1   (1,0)=51.1   (1,1)=49.9
       └── R 最高 ──┘                        └── B 最低 ──┘
```
**R > G > B = 暖光照明**，与画面里那盏黄灯吻合；相位若反会算成 **B > G > R（冷光）**，与肉眼矛盾。
⇒ **真·BayerRG，`cv2.COLOR_BayerRG2BGR` 是对的。**
⚠️ 最亮的 2% 已饱和到 255（无判别力）—— 判别是靠**全图**平面均值做的。

#### ② debayer 开销（实测，两个数别搞混）

| 量法 | 值 |
|---|---|
| **墙钟**（OpenCV 会并行） | 0.09 ms/帧 —— **对 CPU 紧张的机器这个数没有意义** |
| **CPU 时间**（真正该看的） | **1.46 ms/帧** ⇒ 两路 2.92 ms = **46ms 预算的 6.4%** |

⇒ debayer **可以接受**，不是拦路虎。

### 9.15 ✅ 2026-09-25：自建相机驱动 `v4l2_camera`（模块 30）—— **端到端延迟 850ms → 72ms**

**结果**（同一探针、同一台相机）：

| | 相机源年龄 | **端到端 `frame_age_sec`** |
|---|---|---|
| `usb_cam` | 810 ms | **0.83 ~ 0.92 s** |
| **`v4l2_camera`（本仓库自建）** | **47 ms** | **0.072 ~ 0.075 s** |

**降了约 760 ms（约 12 倍）。** 对照预算 warn 56 / error 80 ms：从**超 error 十倍** → **落在 warn 带内**。
其余验收：`/camera_wide/image_raw` 29.0 Hz、`/perception/camera/frame` 30.0 Hz、槽状态 `[1,0,1,0,1,0,0,0]`（有数据的槽是 `FRESH`）。

#### ① 根因：**是 `usb_cam` 的时间戳错了，不是画面真的旧**

四条排除（都是实验，不是推测）：

| 假设 | 实验 | 结果 |
|---|---|---|
| 订阅端大消息排队 | 同节点另发的 `camera_info`（**几十字节**）与 2.76MB 图像**年龄一模一样**（都 810ms） | ❌ 排除 |
| 时钟域漂移 | 连采 42 s，年龄恒定 729~736ms 不漂；`realtime−monotonic` 纹丝不动 | ❌ 排除 |
| 按数据量的队列 | 640×480 比 1280×720 **更差**（640 vs 319 ms） | ❌ 排除 |
| N 帧队列 | 改帧率：30→850ms、15→**242ms**、10→610ms —— **不单调** | ❌ 排除 |
| **自建采集器对照** | 同一台相机换成"时间戳 = 发布时刻" | ✅ **170ms（Python）** ⇒ 差异在 usb_cam |

**⇒ 落在 `usb_cam` 自己写 `header.stamp` 的那一步。**
⚠️ 最可能的机理：它在**初始化时只算一次**"单调钟→ROS 钟"的偏移；之后系统时钟被 NTP 步进/驯服过，
那个偏移就**永久错**了 —— 症状恰好是"**恒定几百 ms、跨次运行不同、单次运行内不漂**"，与实测完全吻合。
**⇒ 本节点每帧重算那个偏移**（`stamp_from_buffer()`）。

#### ② 三个关键设计决定（都写进头文件了）

1. **QoS = `best_effort` + `depth 1`** —— 任务书 §3.0「三相机并行硬约束」第 2 条，
   `image_preprocessor.cpp:111-117` 已记着"**晚了就丢，不堆积**，否则延迟永久滚大"。
   ⚠️ 顺带修掉 `usb_cam` 发 **RELIABLE** 而六路检测器收 best-effort 的**不匹配**。
2. **`timestamp_mode` 是显式参数，默认 `capture`**（诚实），`publish` 只用于对照排查 ——
   后者会把真实采集延迟**藏起来**。⚠️ 每帧把两者差值上报到 `~/capture_diagnostics`，
   **那就是"画面到底旧不旧"的判据，别关掉**。
3. **独立采集线程**（不用 ROS 定时器）：定时器 + 单线程执行器会让"解码 + 2.76MB 序列化"
   与"等下一帧"互相排队。

⚙️ 另外把 `V4L2_CID_EXPOSURE_AUTO_PRIORITY=0`（"暗光下拉长曝光、自动掉帧"）**搬进节点**——
原来是 launch 里用 `ExecuteProcess` 调 `v4l2-ctl` 干的，依赖外部工具、不可复现。

#### ③ 验了什么 / 局限

| 手段 | 覆盖 | 局限 |

### 9.16 ✅ 2026-09-25：海康 GigE 驱动 `mvs_camera` 落地 —— **完整相机方案跑通，端到端 36ms 达标**

**结果**（用户 2026-09-25 拍的板：**海康当 tele + JR720 当 wide**）：

```

② 订阅端年龄    wide 48 ms                    tele 31 ms

#### ① 为什么必须单开一个驱动

海康 `MV-CS020-10GC` 是 **GigE**，**不产生 `/dev/video*`**
（`v4l2-ctl --list-devices` 里没有它）⇒ **`v4l2_camera` 那条 V4L2 路根本够不着它**。
它只能走海康 MVS SDK（`/opt/MVS`）。

⚠️ **MVS 是外部 SDK，不在 ROS 生态里** ⇒ CMake 里做成**找不到就只警告、不构建**，
绝不能让没装 MVS 的机器整个包编不过。

#### ② 时间戳单位是**实测出来的**（不是猜的，猜错就重犯 usb_cam 那个错）

`MV_FRAME_OUT_INFO_EX::nHostTimeStamp` 官方文档**只写"主机生成的时间戳"，没写单位**。

#### ② 与任务书的**有意偏差**：不做匈牙利

任务书 §4.3 写「实现**匈牙利算法**」。**本实现不做** —— 按用户 **2026-09-19 拍板**：
> 本项目落点**全是已知位置**，"观测↔目标"是**查表/落区判定**，不需要匈牙利二分图匹配。

⇒ 实现成**两级**：

| 级 | 判据 | 适用 |
|---|---|---|
| **① 落区认领** | 观测落在某个**已知位置**的区域内 ⇒ 直接认领 | 建筑位 / 两根柱子 / 穆斯蒂卡柱（位置**已知**） |
| **② 就近指派** | 剩下的按三维距离**贪心**，带 `gate_m` 门限 | 数量未知的（对手 BR / TR / 掉落方块） |

#### ③ ⚠️ **核心语义：① 优先于 ②**（改错了不报错）

一个观测可能**离 track A 更近**，但它**落在 track B 的已知区域内** ⇒ **必须认 B**。
理由：A 的位置是**滤波估计**（会被运动/噪声带偏），B 的位置是**场地事实**（常量）——
**拿估计值去压常量，等于把唯一确定的东西弄丢**。

⚠️ **若改成"纯就近"**：症状是**建筑位归属偶尔串位** —— **不报错**，只在特定位姿下偶发，
而它下游连着 `kalman_tracker` 的 id、再下游连着那 40/80 分的 `top_color` 归属。
⇒ 单测里专门有一条 `观测离A更近但落在B的已知区域内时必须认B` **钉死它**。

#### ④ 另外三条写进契约、并各有用例钉住的语义

- **返回与观测等长同序**（未匹配的 `track_index = -1`）：若改成"只返回匹配上的"，
  调用方就得自己判断哪条没配上 —— 那是**漏建候选 track** 的温床。
- **超门限不硬塞**：该观测应去建新候选，而不是塞给最近的 track（硬塞 = 噪声污染已有目标位置）。
- **落区只看水平 xy、不判 z**：雷达在斜视角下**对 z 的估计最差**，带上 z 会让
  "明明就在那个位上"的观测频繁认领失败。⚠️ 代价是正上/正下方也会被认领，对场地布局可接受。
- **持握目标拒绝雷达关联**（「v1.3」）：点云与夹爪粘连、或方块不在建筑位上方被
  `building_spot_analyzer` 忽略 ⇒ 拿雷达去"纠正"它只会把它拽错。**相机仍可配**（那正是持握的判据本身）。

#### ① 为什么这套反算值得单测（P0-3 就是为它立的项）

训练用 **letterbox**（等比 + 补边）⇒ 检测框坐标是"**缩放并补边后**"的，必须反算回原图 ——

#### ② ★★ 最贵的一条：**位置 vs 尺度，两条反算不能混用**

头文件点名「这是整套反算里**最易错的一处**」：
> 反算**尺度类**量（半径 / 宽 / 高）⚠️ **只除 scale，不减填充偏移** ——
> 减了会算出负数或错尺寸。把 width/height 当位置一起减偏移，**在小目标上会直接出负宽度**。

用例把那条陷阱**量出来**：`h=8px` 的小目标、`pad_y=12`、`scale=0.5`，
走位置反算得 `(8−12)/0.5 = −8` ⇒ **负高度**；走尺度反算得 `+16` ✓。
⚠️ 症状是"**某些小目标检不出来**"（半径负 ⇒ 圆形度算不出 / 面积过滤把它当噪点），**不报错**。

#### ② 另外两条刻意钉住的语义

| 语义 | 为什么 |
|---|---|
| **负 age ⇒ FRESH**（不是 STALE） | 负 age = 时间戳在**未来**（时钟跳变/驱动异常）⇒ 那是"**钟不对**"，不是"数据旧"。⚠️ 且 `stale_sec` **如实报负值、不钳到 0**（钳了就掩盖了那个异常） |

另有一条 `三档互不相同`：`NEVER`/`FRESH`/`STALE` 的数值不能撞 —— 撞了下游就分不出
"**没装上**"和"**慢了**"，而那两个的**现场排查方向完全不同**（`msg/SlotStatus.msg` 原文）。

### 9.32 ✅ 2026-09-25：模块 6 `building_spot_detector` 的**四边形几何验证**单测（相机层第 3 个）

**结果**：`validate_angles` / `validate_opposite_sides` 提成 **static + 阈值传参**
（成员退化成薄包装）+ `test/test_building_spot_detector.cpp`（**10 例全绿**）。
全量 **22/22 测试目标、465 例**，整包编译 0 错。

⚠️ **模块 6 仍标 🧱 不是 🟢**：绿 mask / 轮廓 / 凸度 / 填充率 / 发布**一行没测**。

#### ① 为什么这两条"几行几何"值得测

它们判的是"检出的四边形**是不是一个矩形**"，即"这团绿色**是不是一个建筑位**" ——
而**建筑位是那 40/80 分判色的投影锚点**（位坐标 → 图像 ROI）⇒ 判错了：
**太松** ⇒ 绿色杂物当建筑位（多报位）；**太紧** ⇒ 真建筑位在斜视角下被拒（漏报位）。

#### ② ★ 两条**量出"判据有多松"**的用例（**记录行为，不是断言它错**）

| 用例 | 量出什么 |
|---|---|
| `对边判据偏松_明显不规则的四边形仍通过` | 顶点 `(0,0),(10,0),(10,10),(5,8)` 这种**明显不规则**的四边形，手算 `side_score ≈ 0.83 > 0.70` ⇒ **通过**。⚠️ 而且"平行度"用 `\|dot\|` ⇒ 对**等腰梯形**这类"两腰镜像"的形状给出接近 1 的值 —— **它测的是"两腰都够陡"，不是"两腰平行"** |
| `长条矩形照样满分_本函数不查长宽比` | `validate_opposite_sides` 的"长度比"比的是**对边**（0↔1、2↔3），**不是相邻边** ⇒ 一个 100×10 的长条两组对边各自等长 ⇒ `score = 1.0` **满分**。**本函数完全不查长宽比**，一条细长绿条**靠它拦不住** |

⇒ **真正拦住不规则形状的是 `min_convexity_`(0.88) 与绿色填充率那几条** —— 这个分工现在写下来了。

#### ③ ⚠️ 两条**我自己想当然写错的假设**（都是用例当场抓的）

- **"长宽比 10:1 该被拒"** —— 错了，理由见上表。
- **`一个角偏离过大直接拒不看评分`** 那一条：我构造的 `(0,0),(10,0),(10,10),(1,3)` 确实被拒了，
  **但拒它的可能不是"硬判据"而是"评分低"** —— 用例里把阈值给 0 才把这两者区分开
  （阈值 0 还拒 ⇒ 只可能是硬判据）。

⇒ 又一次印证：**"用例红了"先怀疑构造**；而**"用例绿了"也要问一句"它到底验中了什么"**。

#### ① ⚠️⚠️ **抓出一段死代码**（"改它不生效"最难发现的那种）

`validate_pillar` 的 3b「尺寸合理性」：
```cpp
const float est_distance      = (focal_length_px_ * pillar_diameter_) / max(bbox.width, 1);
const float expected_height_px = (focal_length_px_ * avg_height_m) / est_distance;
if (h < expected_height_px * 0.5f || h > expected_height_px * 1.5f) {
  // 尺寸偏差过大，但仍可能是近距离的大柱子或远距离的小柱子
  // 不做硬拒绝，降低后续评分        ← ⚠️ **后面没有任何降分代码**
}
```
⇒ 那两个变量**算完就丢**，「**降低后续评分**」这句注释**没有任何实现**。

### 9.23 ✅ 2026-09-25：模块 21 **第三刀** —— `KnownRegion` 接线，**250 分闸门端到端跑通**

**结果**：`KnownRegion` 接线完成，19 的【落区认领】**真的生效了**。
三个场景**端到端验证通过**（合成 `LidarResult` → 节点 → `/perception/fusion/state`）。
全量 **14/14 测试目标、349 例**，整包编译 0 错。

#### ① ⚠️ 接线时发现的**设计缺口**（不接就发现不了）

```
TargetAssociator::KnownRegion::track_id  ← 要求指向一个【已存在的 track】
而普通 add_track 的 id 来自 KalmanTracker::next_id_++（跑着的计数器）
⇒ 建筑位编号(spot_id 0~9) 与 track id 对不上 ⇒ 落区认领【一个也认不到】
⇒ 19 的"落区优先于就近"这条核心语义【整条失效】—— 而它【不报错】
```

**⇒ 新增 `KalmanTracker::add_known_track(id, x, y, z, t, params)`**：调用方**指定 id**
（就用建筑位编号），并顺手做对三件事：

| 行为 | 为什么 |
|---|---|
| 状态**直接 `CONFIRMED`** | 它是**场地常量**，不需要靠观测确认。走 `CANDIDATE` 会让它在确认窗口里**不被输出**，而那段窗口里落区认领照样会认领上它 —— 语义上说不通 |
| `on_known_spot = true` | 「v1.2」它丢了也不该按 LOST 删 |
| 速度协方差给 **`1e-6`**（与普通 track **相反**） | 普通 track 是"位置已知、速度未知"（给 100）；而建筑位**压根不会动** ⇒ 给大协方差等于**允许滤波器把它拽走**，那正是"塔归属串位"的另一种成因 |

⚠️ 并把 `next_id_` 抬到 `id + 1` 之上 —— 不抬的话之后的普通 track 会**撞号**
（撞号 = 下游把两个目标混为一谈、追踪"跳"过去）。

#### ② ★ 三个场景**端到端验证通过**（这是那 250 分闸门第一次真的跑过）

```
A: 2 塔，1 座在共享位(4)        ⇒ sanctuary_mandate_fulfilled=1  sanctuary_valid=True   ✓
B: 2 塔都在【非共享】位          ⇒ =0  True    ✓  ← **最阴的那一档**（塔数够了但没共享位）
C: 同 A 但有一位 state=UNKNOWN(4) ⇒ =1  False   ✓  ← 结论不可信必须如实标出来
```

判据**不是"节点活着"**，而是**真发消息、真读回**（`ros2 topic pub` 合成 `LidarResult` →
读 `/perception/fusion/state` 的字段值）。⚠️ 且**用的是真配置**
（`--params-file config/field_geometry.yaml` ⇒ 10 个建筑位坐标是**场地真值**，不是造的）。

#### ③ 一个测试时序坑（记下来免得再踩）

⚠️ `ros2 topic echo --once` **必须先订阅上**才接得到那一条。我第一次写成
"先 pub 再 echo" ⇒ echo 一直在等**下一条**（而节点只在收到雷达结果时才发）⇒ 读不到。
⇒ 正确写法：**持续 pub (`-r 5`) + 先起 echo**。
（ROS 的话题发现本身也有延迟，`--once` 那种一次性 pub 很容易错过。）
