## 一、为什么要做

### 1.1 现状：同一套算法存在两份实现

| | 单体 `lidar_perception_node.cpp` | 5 个独立组件 |
|---|---|---|
| 规模 | 1570 行 | 3160 行（preprocessor 395 / ground 539 / cylinder 779 / cluster 806 / spot 641） |
| 形态 | `rclcpp::Node`，自带全套 PCL 管线 | 5 个 `rclcpp::Node` 子类 |
| 被谁启动 | `bringup_full` / `bringup_lidar_only` / `bringup_gazebo` | **没有任何 launch 启动** |
| 发布 | `/perception/lidar/{ground,non_ground,l0..l2_surface,ground_plane,pillars,obstacles,building_spots,filtered,result,debug_cloud}` | 同名话题的子集 + `diagnostics` |

**两者不是"两套不同的实现"，是同一套代码的复制。** 证据：`GroundSegmenter` 的方法集
（`validate_plane_normal` / `refine_inliers_adaptive` / `classify_by_platform` / `normalize_coefficients`）
与单体内 869–935 行的同名方法**一一对应，连名字都一样**。

副作用：**同话题双发布者，且 QoS 不同**（组件用 `SensorDataQoS`，单体用 `SystemDefaultsQoS`）。
任何一方被误启动，`/perception/lidar/ground` 就有两个发布者，下游行为不可预测。

### 1.2 拆分留下的伤

- **18 个参数名对不上**：`lidar_params.yaml` 里的键与代码 `declare_parameter`/`GET` 的名字不匹配，
  写了不生效。典型是短的 `top_surface_min_pts`（单体用）与长的 `top_surface_min_points`（组件用）并存，
  yaml 只跟了一边。
- **§11.1 的 10 个单测无处落脚**：算法长在 `rclcpp::Node` 里，测一个算法要先起 ROS。
- **§6.1 的零拷贝与分模块耗时统计无从谈起。**

### 1.3 目标

1. 算法只留**一份**，成为可独立单测的纯算法类
2. 按 §6.1 的三条流水线容器化，大块点云**从不跨容器边界**
3. 参数名收敛为一套，可由 yaml 调到
4. 保留现有编排能力（看门狗、统一输出、诊断）

**非目标**：不追求"每个算法一个可 `ros2 component load` 的节点"（见 §3.3 的取舍）。

## 二、现状接线（重构前的事实基础）

组件其实已构成一条完整链：

```
/livox/lidar/pointcloud ─→ [lidar_preprocessor] ─→ /perception/lidar/filtered
    (还订阅 /robot_pose, 自过滤用)
        └─→ [ground_segmenter] ─→ ground / non_ground / ground_plane
              ├─→ [cylinder_detector]     ─→ /perception/lidar/pillars
              ├─→ [cluster_extractor]     ─→ /perception/lidar/obstacles
              └─→ [building_spot_analyzer] ─→ /perception/lidar/building_spots
```

三个下游并行，都消费 `non_ground`。

**关键缺口**：雷达层**完全没用自定义 msg** —— `pillars`/`obstacles`/`building_spots` 都是
`visualization_msgs/MarkerArray`（给 rviz 看的），`result` 是 `diagnostic_msgs/DiagnosticArray`（给人看的）。
`msg/` 下已定义好的 `Obstacle` / `BuildingSpot` / `PillarStatus` **一个都没被使用**。

## 三、目标架构

### 3.1 容器边界 = §6.1 的三条线程

```
┌─ 容器 A：雷达线程 (core 0–1) ───────────────────────────┐
│  lidar_pipeline  ← 薄壳组件节点                         │
│    ├─ LidarPreprocessor      ┐                          │
│    ├─ GroundSegmenter        │ 纯算法类                 │
│    ├─ CylinderDetector       │ 不碰 ROS                 │
│    ├─ ClusterExtractor       │                          │
│    └─ BuildingSpotAnalyzer   ┘                          │
│  算法之间传 pcl::PointCloud::Ptr —— 进程内直接调用      │
│  发布: /perception/lidar/{...} + /perception/lidar/result│
└─────────────────────────────────────────────────────────┘
        ↓  /perception/lidar/result  (LidarResult, 几 KB)
┌─ 容器 C：融合+编码线程 (core 4) ────────────────────────┐
│  fusion_node                                            │
│    CoordinateTransformer / KalmanTracker /              │
│    TargetAssociator / LidarCameraFusion / ScoreEstimator│
│  输入: LidarResult + 相机结果 + /aft_mapped_to_init     │
│  输出: /perception/output = PerceptionFrame             │
└─────────────────────────────────────────────────────────┘
┌─ 容器 B：视觉线程 (core 2–3) ───────────────────────────┐
│  camera_pipeline ← 薄壳                                 │
│    ImagePreprocessor / MustikaDetector /                │
│    BuildingSpotDetector / PillarDetector                │
└─────────────────────────────────────────────────────────┘
      Point-LIO 单独占 core 5（它自己就是 CPU 大户）

  perception_pipeline：生命周期 / 热管理 / 降级（跨容器编排，尚未开工）
```

### 3.2 核心决策

**决策 1：单体节点不消失，它变成薄壳。**
`lidar_perception_node` 的**编排逻辑是好的**（订阅、看门狗、统一输出、诊断），坏的只是它把算法又抄了一遍。
保留它作为容器 A 的组件节点，只把方法体换成调用算法类。结构不动，只换内脏 —— 这是迁移风险最低的路径。

**决策 2：5 个组件的 Node 外壳退役，算法进 `lidar_algorithms` 库。**
外壳谁也不留（订阅/发布是同质样板），**算法共同留一份**，做成库，被"容器 A 薄壳"与"单测"共同链接。

**决策 3：零拷贝靠结构达成，不靠 `use_intra_process_comms`。**
容器内算法之间是函数调用，传 `CloudPtr`，**一次拷贝都没有**；跨容器传的是几 KB 的结果，
大块点云从不过边界。intra-process 只在"确实要点云跨节点"时才有意义，本设计没有这种情况。

**决策 4：热管理用算法级 + 发布级开关，不用节点级。**
任务书 §13（第 953 行）要求无风扇平台 90°C 降频时"关后相机推理 / 前相机降到 480×288 /
**暂停调试点云与图像发布**"。最后一条用节点级启停做不到 —— 只停发布、不停管线。`Params::enabled` 可以。

### 3.3 取舍说明（与"每模块一个节点"的对比）

| | 每模块一个节点 | 本设计（三条流水线） |
|---|---|---|
| 零拷贝 | 达不到（每级 `toROSMsg`+`fromROSMsg` 两次点云拷贝） | 真达到 |
| 独立启停 | 节点级，最灵活 | 算法级开关（更细，且不重启） |
| 容器内调度 | 8 个节点在 **8C16T**（本机 7840HS）上可接受 | 3 个节点 |
| 与 §6.1 对齐 | 形状像、实质不符 | 完全对齐 |

选后者：**8C16T 有富余**（原写 6C12T；2026-09-25 按本机 7840HS 更正），
但省不掉的是**内存带宽的账**，而非核数的账 —— ⚠️ 本机内存只有 ~12.5GiB，这本账比核数更紧。

## 四、算法类接口规范

```cpp
namespace br_perception::lidar {

using CloudPtr = pcl::PointCloud<pcl::PointXYZI>::Ptr;

struct GroundResult {
  CloudPtr ground, non_ground;
  CloudPtr l0_surface, l1_surface, l2_surface;    // 热管理降级时可为空
  pcl::ModelCoefficients::Ptr plane;
  double elapsed_ms{0.0};                          // §6.1 分模块耗时统计
};

class GroundSegmenter {
public:
  struct Params {                                  // 参数归算法类所有, 不认识 ROS
    double ransac_dist_thresh{0.04};
    int    ransac_max_iters{100};
    bool   enabled{true};                          // 算法级启停 (热管理降级)
  };
  explicit GroundSegmenter(const Params& p);
  GroundResult segment(const CloudPtr& in) const;  // 纯函数: 不订阅、不发布、不碰 Node
private:
  Params p_;
};

}  // namespace br_perception::lidar
```

**四条硬性规则：**

1. **算法类不碰 ROS** —— 构造不接 `Node*`、不 `declare_parameter`、无订阅发布。输入输出都是 PCL/STL 类型。
   这是 §11.1 单测能真正落地的前提。
2. **参数由薄壳统一声明后填进 `Params`** —— yaml 只保留**一份键名**，以算法类字段名为准。
   旧的短名/长名合并成一个，18 个对不上的问题在此一次清掉。
3. **诊断与耗时由算法类返回、薄壳汇总发布** —— `elapsed_ms` 等进 `DiagnosticArray`。
4. **`Params::enabled` 实现降级** —— 关掉某个算法 ≠ 停容器。

**文件布局**：
```
src/lidar/algorithms/{lidar_preprocessor,ground_segmenter,cylinder_detector,
                      cluster_extractor,building_spot_analyzer}.cpp
src/lidar/include/br_perception/lidar/algorithms/*.hpp
CMake 库目标: lidar_algorithms
```

## 五、消息接口

### 5.1 新增 `msg/LidarResult.msg`（容器 A → 容器 C 的正式接口）

```
std_msgs/Header header          # frame_id = "world", 带时间戳
Obstacle[] obstacles
BuildingSpot[] building_spots
PillarStatus mustika_pillar
PillarStatus core_pillar
float32[] stage_elapsed_ms      # 各阶段耗时 (§6.1)
bool watchdog_ok                # 雷达在线 (替代现在塞在 DiagnosticArray 里的做法)
```

替代现在拿 `DiagnosticArray` 当数据接口、拿 `MarkerArray` 当结果的做法。
`MarkerArray`/`debug_cloud` **保留但只作可视化**，不再承担数据职责。

### 5.2 `msg/PerceptionFrame.msg` 改动

| 改动 | 原因 |
|---|---|
| `builtin_interfaces/Time timestamp` → `std_msgs/Header header` | 现在丢了 `frame_id`，不符合 ROS 惯例；且下游无法知道坐标系 |
| `uint32 frame_id` → 改名 `uint32 seq` | 与 `Header.frame_id` 语义撞名 |
| `geometry_msgs/Pose2D mustika_pose` → `geometry_msgs/PoseStamped` | **"柱上 vs 被拿起"靠高度区分，Pose2D 丢了 z** |
| 新增 `uint8 match_remaining_sec` | §5.1 协议要求（v1.6 新增，感知自计时） |
| 新增 `uint8 held_object_count` | §5.1 协议要求（v1.6） |
| 新增 `uint8 holding_over_limit` | §5.1 协议要求（v1.6，规则 4.4.2 BR 限持 2 块） |
| 新增 `uint8 match_end_release_warning` | §5.1 协议要求（v1.6，规则 8.6.1） |
| 新增 `uint8 sanctuary_mandate_fulfilled` | §5.1 协议要求（v1.2，规则 4.5.1） |
| `mustika_state` 注释补 `6 = RETURNING_RETRY` | 规则 4.6.3 重试归还中 |

**为什么现在改最便宜**：`PerceptionFrame` 目前**没有任何消费者**（`fusion_node` 还没写），
改动代价为零。等融合节点写出来再改就要动两处。

## 六、迁移顺序与验收

### 阶段 0 —— 录基准 bag（**必须在动手之前**）

```bash
ros2 launch br_perception bringup_gazebo.launch.py
ros2 bag record -o baseline /livox/lidar/pointcloud /perception/lidar/ground \
  /perception/lidar/non_ground /perception/lidar/pillars \
  /perception/lidar/obstacles /perception/lidar/building_spots
```

这份 bag 是后续每一步的对照物，也是 `test/test_data/sample_bag/`（§11.2）的素材。
**没有它，后面所有"验收 = 与改前一致"都无从谈起。**

### 阶段 1 —— 搭骨架

建 `algorithms/` 目录、CMake 库目标 `lidar_algorithms`（先只装一个算法）。
验收：`colcon build` 通过，`liblidar_algorithms.so` 存在。

### 阶段 2–6 —— 逐算法搬迁

顺序按依赖链：`lidar_preprocessor` → `ground_segmenter` → `cluster_extractor` →
`cylinder_detector` → `building_spot_analyzer`

每个算法固定四步：
1. 算法体从组件搬进 `algorithms/X.cpp`，包成 `class X` + `Params`
2. 单体里对应方法体改为调用 `X::run()`
3. **删掉单体里那份重复实现**
4. 删掉组件的 Node 外壳

**同步写单测**（§11.1 对应项）：`test/test_<算法名>.cpp`，用阶段 0 的 bag 作输入，
断言点数/质心/分类结果。

验收：`ros2 bag play baseline` → 新管线重跑 → 逐话题对比。判定标准：

- **首选 bit 级完全一致** —— 搬的是同一份代码、同一份输入，结果本就应该逐点相同
- 若因浮点累加顺序变化出现极小差异，允许**点数差 ≤0.1%、质心差 ≤1mm**
- **分类标签（方块类型 / 建筑位状态 / 塔顶颜色）必须 100% 一致** —— 这类差异不接受"容差"
- `ground_plane` 法向量夹角 ≤0.5°

不一致就说明搬的过程中改动了逻辑，要查清楚再继续，不能带着差异往下走。

### 阶段 7 —— 容器化

写 `lidar_container`（component container）+ 改 launch。
验收：`ros2 component list` 能看到节点；话题输出与阶段 6 一致。

### 阶段 8 —— 消息接口 + 融合容器

落地 §5.1 / §5.2 的消息定义，`fusion_node` 进容器 C。
验收：端到端 `/perception/output` 有 `PerceptionFrame`。

### 回退

每个阶段一个 commit，出问题 `git revert` 那一个提交。
