# BR 强化学习决策与导航方案

> 状态：按《竞技赛主题与规则 V3（第 3 次修订，文件日期标记 5/11/2026；日期格式待核）》重排后的推荐设计，待按阶段实施。
> 本文补充《任务_v1.7》和现有仓库，不替代正式规则、安全和感知契约。V3 PDF 是当前规则事实源；规则正文与附录存在分值冲突，见第 5 节，未裁定前不得训练成固定常数。
> GitHub 工程参考：[CleanRL](https://github.com/vwxyzjn/cleanrl/tree/fe8d8a03c41a7ef5b523e2e354bd01c363e786bb)（PPO 细节与可复现实验）、[Stable-Baselines3](https://github.com/DLR-RM/stable-baselines3/tree/0cdcd200deef06b9ad0af72f6ddfb07c06c6df39) / [SB3 Contrib Maskable PPO 文档](https://sb3-contrib.readthedocs.io/en/master/modules/ppo_mask.html)（非法动作屏蔽）、[Nav2](https://github.com/ros-navigation/navigation2/tree/b798842e54d7d5bded51244fced5d1130cad2784)（导航任务与恢复行为分离）。这些项目只提供工程方法，不提供 BR 的规则、动作或分值。
> 目标：让 BR 能根据对手、阻挡、任务收益和剩余时间改变行动，同时保留可验证的安全边界。

## 1. 结论与范围

采用**分层、基于结构化状态的强化学习**。策略不读取相机图像或原始点云；它读取感知与融合层产出的目标、置信度、时效、位姿、塔况、资源和比赛状态。首版只训练比赛任务策略；导航通行、恢复和跨层运动先由确定性路网与行为状态机执行，待闭环数据充分后再单独评估局部 RL。

本方案把强化学习用于比赛任务决策，把运动执行与恢复保留为确定性层：

1. **比赛策略层（首版 RL）**：学习有限时长内做什么、何时切换任务，以及如何权衡建塔分、塔顶归属、公共区风险、五色石机会和剩余时间。
2. **执行与恢复层（首版确定性）**：在已验证路网、区域和运动原语上继续、等待、退让、重定位、重试或放弃目标；以后若有必要，再把其中一个受限动作集合单独做局部 RL。

策略不直接输出轮速或未经约束的连续 `cmd_vel`。跨层路径仍使用赛前验证的路网边，选定的运动选项交给确定性跟踪器执行。TR/BR 角色区域、BR 进入 L1/L2 的条件、持物上限、五色石互斥持物、保护法则、强制重试、终场停止和急停等硬约束由规则/安全状态机控制，不能交给奖励函数保证。

## 2. 现状与新增工作

仓库已有 ROS 2 Humble/C++17 感知、Point-LIO、融合与计分相关代码，结构化信息包括 `PerceptionFrame`、`FusionState`、障碍物/目标消息、场地几何配置和部分比赛判定。现有策略输入可从这些接口组合，但还没有完整的任务决策与导航执行链。

仓库有 Gazebo 场地、传感器载具和 `sim_patrol.py` 巡游。当前仿真主要验证传感器、定位与感知通路，不包含足够完整的 180 秒比赛流程、双方策略、资源交接、方块/塔动态、任务得分闭环或导航控制。因此它**不能直接作为比赛策略的训练环境**。需要先建立可快速运行、按规则记分并支持随机场景的比赛环境，再逐步用 Gazebo 验证局部运动行为。

现有方案把“跑点 + RPP”列为导航主线，但代码中尚无完整路网、路线调度和比赛任务执行器。新方案不是给已存在的完整导航栈增加 RL 插件，而是定义这条新增链路的架构和实施顺序。

本机 `D:\Anaconda3\envs\rl` 已安装 Python 3.11、MuJoCo 3.15、Gymnasium 1.4、PyTorch 2.11 CUDA；当前未安装 Stable-Baselines3，仓库也没有现成 MJCF。可直接做 Gymnasium 环境和 MuJoCo 模型原型；采用 SB3 Contrib Maskable PPO 前需在该环境补装并锁定依赖，或者用 CleanRL/PyTorch 训练并自行实现训练/采样一致的合法动作 mask。

### 2.1 场地图复用

`config/field_geometry.yaml` 作为静态场地几何的唯一来源，统一提供 ROS 路网、快速规则环境和 MuJoCo 场地生成器的边界、层高、共享区、储存/传递区、建塔位、坡道及地面-L1阶梯。仓库配置已将 L1-L2 阶梯标为 `enabled=false`，与 V3 修订记录/术语一致；V3 正文仍残留相反描述，因此生成场景和模型时保留规则版本/几何版本标识，并在正式场地确认后冻结。

不要在 YAML 和 MJCF 各自维护坐标副本。生成器从 YAML 产生 MuJoCo 静态地台、墙/栏、斜坡/阶梯、区域碰撞体和建塔位标记；在 MJCF 中只维护机器人刚体/驱动器、可移动比赛用品和物理参数。规则对局环境可以用同一 YAML 生成区域图与距离/通行时间，不需要为每个 180 秒策略 rollout 都运行刚体仿真。

## 3. 系统结构

```text
相机 / 雷达 / Point-LIO
          │
          ▼
感知与融合：目标、塔况、位姿、置信度、时间戳、比赛事件
          │
          ▼
状态构造器：归一化、时效检查、历史差分、合法候选动作
          │
          ├── 比赛策略 Maskable PPO：选择任务 / 目标 / 任务切换
          │
          ├── 确定性导航与恢复：路网跟踪 / 等待 / 退让 / 重定位 / 重试
          │
          ▼
安全过滤器：规则、区域、速度、状态新鲜度、动作合法性
          │
          ▼
行为执行器：路网跟踪器 / RPP 或等效确定性控制器 / STM32
```

训练与部署分离：Python 负责环境、训练、评估和模型导出；ROS 2 主机上的策略节点加载小型 ONNX actor，按状态输入输出候选任务分数。动作掩码、安全规则、状态校验和回退逻辑留在 C++ 节点中，保证模型不能绕开执行边界。策略推理使用独立节点，不进入感知热路径。

### 3.1 V3 规则事实与未裁定项

规则来源是随仓库提供的《第二十六届全国大学生机器人大赛女娲补天竞技赛规则 V3（征求意见稿）》；PDF 第 29 页说明组委会可继续发布修订，因此规则、训练场景和模型必须携带规则版本。以下“规则事实”摘自 V3 条文；修订历史、说明框和编者评论用于理解文档，但不视为独立规则命令。正式执行时以组委会发布的最新正式版本和裁判解释为准。

| 项目 | V3 条文对决策系统的约束 | 建模处理 |
|---|---|---|
| 比赛时长与停止 | 180 秒；结束信号后机器人立即停止，仍被机器人接触/夹持/支撑的比赛用品不计分 | 终场状态机独立于 RL；预留停车与松手时间，180 秒按正式计分快照核分 |
| TR / BR 分工 | TR 可手动或自动，只在地面区活动并经坡道/阶梯到传递区；BR 全自动，在传递区、L1、L2 活动，启动或重试后可在进入坡道/阶梯前处于地面，进入 L1 后不可下返（重试例外） | 两个机器人分别建模；BR 不接收 TR 信号，只能自主观测环境；初期策略只部署在 BR |
| 搬运上限 | TR 最多 3 个塔基/中段/塔顶；BR 最多 2 个；持五色石时不得携带其他用品 | 合法动作掩码 + C++ 执行前复核；未知持有量时屏蔽取物/交接动作 |
| 建塔与失误 | 塔基→中段→塔顶；投影不能越出建塔处；失误物品作废并移除，不导致强制重试；传递分仍有效 | 环境按事件精确转移；非法放置不能靠 shaping reward 奖励 |
| 保护法则 / 五色石 | 需同时有至少两座全塔，且至少一座在 L1 公共建塔处或 L2；达成后即使塔被改动仍视为永久满足。TR 取石后在传递区直接交给 BR，BR 运至 L2 中央基座 | 设置 `mandate_satisfied_once` 单调锁存状态；终极目标候选动作仅在资格与流程状态合法时开放 |
| 公共区与撞塔 | 公共区不得故意阻挡/妨碍对手；导致塔倒塌或塔上物品移位即犯规，无论有意与否 | 隔离对手碰撞/阻挡状态；安全约束避免接触塔和对手机器人，不鼓励堵路或碰撞 |
| 重试与罚时 | 犯规强制重试；强制重试在重试区至少 15 秒且经裁判许可后再启动，比赛计时不停；BR 至少进入 L1 一次后可选 L1 重试区 | 重试是显式事件和 15 秒以上时间损失；裁判许可为外部输入，策略不能自行复位 |
| 机器人自治与安全 | BR 全自动；TR 与 BR 禁止任何方式相互通信；只允许规定的启动/暂停恢复射频；实体有线急停，禁止远程急停 | 不新增车车数据链；暂停/恢复只在裁判许可接口上使用，急停仍为独立实体安全链 |
| 场地 L2 结构 | V3 修订历史文件日期标记为 `5/11/2026`；第 13 页术语称 L1 与 L2 之间没有阶梯、BR 可从 L1 任意位置登上 L2；但第 10 页正文仍称有一级阶梯 | **规则文件内部冲突**。仿真/路网参数需单独版本化；`field_geometry.yaml` 当前禁用了该阶梯。按最终场地核对后冻结几何，不以歧义文字擅自改写实场地图 |
| 分值与持石重试 | 正文 8.1.5 五色石 250 分；附录 2 列 255 分且说明部分条目含 5 分搬运分。5.1.3 强制重试持石时移出场地；5.3.2 重试持石时放在 L1 留待核分 | **规则文件内部冲突**。记分引擎先分别实现正文/附录版本测试，不叠加或猜测；训练默认关闭五色石高风险策略，直到主办方书面裁定分值与重试处置 |
| 平局 | 总分相同依次比较：成功放石、全场顶面同色塔顶数、L2 正确得分物品数、L1 正确得分物品数，最后由裁判评定技术与体育精神 | 评估报告记录完整字典序指标；训练优化以总分为主，并用经规则确认的平局顺序做次级比较 |

正文 8.1.1 对 TR 运送的每件用品给 5 分，而附录某些塔基/中段/放石行把搬运分并入分值，另有单列运输分。计分器应以规则裁定后的最终记分表口径核算，不能把动态记分事件重复累计。

## 4. 状态、动作与决策时序

### 4.1 状态表示

策略输入为固定结构、单位明确、归一化后的向量，不输入图像、点云或自由文本。状态至少覆盖：

| 状态组 | 特征 |
|---|---|
| 自身 | `world` 位姿、航向、速度、所在区域/路网边、当前任务、夹爪/持握种类数量及有效位 |
| 比赛时钟 | 剩余时间、终场停车窗口、重试/复位状态、强制重试剩余等待时间 |
| 塔与比赛用品 | 各建塔处塔基/中段/塔顶颜色朝向、结构有效性、观测置信度与年龄；各用品位置/持有者/有效状态；五色石资格与流程状态 |
| 动态场面 | 最近 K 个障碍/对手的相对位置、速度、类别、置信度、年龄、所在区域及对己方目标的威胁 |
| 路网局部 | 当前边通行状态、前方可见距离、可选相邻边、预计时间、坡道/楼梯/窄口标签、阻塞持续时间 |
| 执行反馈 | 最近动作、是否完成、耗时、失败原因、控制器/定位健康状态 |

所有可缺失信息必须携带有效位或年龄；**未知不能编码成“空”或数值 0**。位置、速度和对象排序采用固定规则（如距离当前机器人最近优先），以保持模型输入稳定。将速度、状态变化量和阻塞持续时间显式放入状态，减少只看单帧造成的部分可观测性；第一版不使用循环网络。

#### 与当前消息的接线边界

第一版状态构造器必须显式区分“已有字段”和“待接入事实”，不能把消息里的占位值当成真值：

| 决策信息 | 当前可用来源 | 接线要求 |
|---|---|---|
| 自位姿与定位健康 | `PerceptionFrame.ego_pose`、`pose_valid`、`odometry_reliable` | 先检查有效位；坐标不可用时只允许等待、重定位和安全回退 |
| 建筑位状态 | `PerceptionFrame.building_spots[]` / `BuildingSpot` | `state=UNKNOWN(4)` 与 `EMPTY(0)` 分开；消费前统一变换到 `world` |
| 障碍与动态目标 | 融合层 `Track[]`，或带 `header.frame_id` 的 `Obstacle[]` | 统一坐标系、置信度和年龄；不能假定所有位置天然是 `world` |
| 相机与感知新鲜度 | `CameraFrame.frame_age_sec`、`SlotStatus.state/stale_sec`，雷达诊断 `age_newest_ms` | 过期数据进入降级状态，不能继续支持高风险动作 |
| 保护法则与五色石 | 由 BR 自主观测的塔状态、五色石状态及锁存比赛事件 | 观测不可靠时按未知处理；未确认满足保护法则前不得执行取石任务；五色石不是 BR 感知侧单独能权威确认的分数事实 |
| 持握数量与夹持确认 | 夹爪编码器/电流、载荷检测或独立物品检测（待定型） | 当前感知层不能权威测量；须增加 BR 本机传感器闭环，不得从 TR 或场外设备接收状态；无效时屏蔽后续搬运动作 |
| 资源、交接和队伍颜色 | 当前消息未提供完整权威台账 | 队伍颜色由赛前本机配置；物品/交接状态由 BR 自身感知和本机执行反馈维护置信台账。严禁接入 TR 信号或比赛中外部设备下发的策略状态；信息不确定时屏蔽依赖它的动作 |

其中 `FusionState.match_remaining_sec` 使用 `int16` 保留超时语义，而 `PerceptionFrame.match_remaining_sec` 目前是 `uint8`；在该契约统一前，策略以主控时钟为权威，不能从 `uint8=0` 判断“刚好到零”还是“已经超时”。

### 4.2 比赛策略动作

上层策略按事件触发或低频周期运行，输出一个短时有效的任务意图：

- 取用/交接可用塔基、中段或塔顶；
- 前往指定合法建塔处，按塔基→中段→塔顶顺序建造或完成塔顶翻转；
- 在满足保护法则且有资格时选择五色石任务；
- 避让公共区对手与已建成塔，选择安全替代建塔处；
- 等待、放弃当前任务、请求重试或进入终场安全状态。

候选动作由当前规则状态动态生成，例如已完成、不可达、资源不足、位姿不可靠或规则不允许的目标直接屏蔽。模型在候选动作分数上选择，不以固定神经网络输出的任意 spot 编号绕过状态校验。

### 4.3 确定性导航与恢复动作

首版导航由固定路网、路径跟踪器与行为状态机执行：沿已验收路段继续、选备选路段、在公共区等待/让行、退至安全节点、重定位、放弃当前目标、按规则申请重试。跨层段使用经实测验收的固定运动原语，不由策略临场生成几何轨迹。导航恢复借鉴 Nav2 将导航任务与 recovery 行为组合的结构，不直接照搬其 ROS 配置或动作参数。

只有在建成路网和控制闭环、能稳定复现动态障碍场景、且确定性恢复基线表现出可量化瓶颈后，才考虑对单一局部决策（例如“等待/选备选边/退让”）训练独立 RL。届时动作仍受同一安全过滤器约束，不和上层任务策略同时首发。

### 4.4 频率与过期处理

比赛策略初始按 1–2 Hz 或比赛事件触发。输入超过配置的新鲜度阈值、关键传感器退化、策略超时或模型加载失败时，停止接受新策略动作并进入确定性回退：规则基线继续决策；若状态仍不足，则停车/等待、请求重定位或申请重试。终场停止与急停继续由独立安全逻辑承担。

### 4.5 建议的首版比赛策略（启发式基线，非规则）

以下是可直接作为确定性 baseline 和 MuJoCo 场景脚本的策略假设；随后由成对对局验证，不把队伍当前机械方案当成不可变前提。

1. **布场一次备足己方物料**：规则允许设置时间内自选放入储存区的塔基/中段数量，每列最多两块；若赛前总装和空间允许，建议把计划使用的己方全部物料一次摆入储存区，避免比赛中发现不足后无法补入。
2. **尽早形成保护法则条件**：BR 先完成己方专属 L1 全塔，再完成一座 L1 公共建塔处全塔；公共塔在保护法则锁存前可能被对方翻顶，故上层策略持续检查“两座同时完整且一座在公共建塔处”的条件，成立即锁存事件并优先衔接五色石流程。若公共路线风险过高，由基线枚举 L2 公共建塔处方案，实际采用哪个取决于最终通行结构和闭环耗时。
3. **TR 将用品直送传递区**：TR 一趟最多三个塔基/中段/塔顶，BR 最多持有两个；按机构取放顺序可行时，一批“塔基+中段+塔顶”正好组成一座塔的物料包。规则只给完全释放在传递区（或进入/伸入传递区的 BR 上）的用品记运输分；把塔顶先放在己方储存区既不产生该运输分，规则也没有把储存区定义成塔顶缓存点，还会增加二次取放和周转。因此默认直送传递区；除非裁判确认允许且实测证明能缩短关键路径，不把存储区暂存列为主策略。
4. **塔顶翻转按收益密度触发**：V3 规则允许把塔顶从原塔抬起翻转后放回同一塔，顶面颜色在翻转完成后改变得分归属。修复一座被翻成对方颜色的己方塔，理论分差摆幅在 L1 为 80 分、L2 为 160 分（我方增加该分值，同时对方失去该分值）；但不代表每次都值得折返。只在状态新鲜、塔结构稳定、预计“分差摆幅/往返与操作总时间”高于当前任务收益密度，且剩余时间能完成并脱离塔体时才派 BR。优先处理 L2 高价值塔，其次 L1 公共塔；已在 L2 时不要为低价值 L1 目标机械往返。
5. **五色石与终局收尾**：保护法则达成后，按经裁定版本的分值和可完成时间判断是否启动取石；持石时不安排其它用品任务。五色石成功放在中央基座后比赛仍继续，BR 应切回塔顶归属维护和得分最高的建塔任务；最后阶段优先完成能在终场前完全脱离机器人、且风险可控的操作。

对“左右两侧夹柱、机械臂处理塔顶”的机械构想，建议按以下职责实现：

- **底盘与爬升机构**：BR 从启动/重试区经地面到 L1 必须使用规定的坡道或三级阶梯。优先做低重心的双履带/大接触长度底盘，先验证三级 150 mm 台阶、3.5 m 坡道、传递区停车和刹停；若速度或稳定性达不到指标，再比较四轮摇臂/摆臂方案。机械臂和夹具在爬升时收拢并锁止，避免抬高重心。L1-L2 按规则最终确认后的场地结构验收，当前 YAML 将旧阶梯禁用。
- **左右夹柱机构**：用左右同步、带柔顺/限力的宽平行夹面夹持 350 mm 塔基/中段，夹爪保持水平并从侧面完整抬离地面；如设计左右两个独立夹位以同时带两件，需能分别开合/确认持有状态，且总数不超过 BR 的两件上限。避免用刚性高夹力把瓦楞纸箱夹塌；取放前检查横向偏差，落位后垂直卸力，不横向抽爪碰塔。
- **塔顶/五色石机械臂**：单独的低惯量机械臂负责从 TR 直接接球、在中央基座放球、取放 200 mm 塔顶和在原塔上翻顶。塔顶用可控夹面定姿；五色石用包络式三点托持/防脱结构，不能依赖摩擦夹紧一个球体。机械臂任一时刻只处理一个高精度目标；携带五色石时左右夹柱机构必须完全空载且不能支撑其它比赛用品。实际末端按 V3 尺寸重量校核，并验证实体有线急停时不继续掉落或伸展。

上述是机械架构建议，不是规则条款。BR 起始时必须完全收在 700 mm 立方体内；完全伸展尺寸受 1400 mm × 1000 mm × 1200 mm 限制。将实际 CAD、质量/惯量、关节范围与本方案场地图一起用于 MuJoCo，按“爬升成功率、每次通行时间、夹持滑落率、建塔偏差、碰塔率、持球掉落率、总质量/伸展包络”验收。若赛场没有传感器能确认物品已夹稳，任务策略不得假设抓取成功，应通过夹爪电流/位置或独立检测闭环确认。

## 5. 学习方法与奖励

首版推荐 **SB3 Contrib Maskable PPO + 小型 MLP**。任务候选是离散动作，规则状态变化会使可选任务变化，训练策略使用合法动作 mask；执行前 C++ 安全层再次独立校验。当前 `rl` 环境没有 SB3/SB3 Contrib，实施时需锁定兼容版本后安装；若不增加依赖，则按 CleanRL 的 PPO 实现细节在现有 PyTorch/Gymnasium 环境实现策略，并测试 mask 在 rollout 采样与更新时完全一致。CleanRL 作为代码级交叉核对，不同时维护两套生产流水线。PPO 只是首选基线，必须与确定性策略在同场景配对评估后才能判断是否更好。

采用 **Actor-Critic 分离观测**：Actor 仅接收比赛时 BR 能通过自身传感器/已允许接口获取的 `DecisionState`；Critic 可在训练时读取仿真真值（对手隐藏状态、准确物品状态、路径真实耗时等）辅助价值估计，但这些特权字段不得进入导出 Actor、动作掩码或部署状态。实机执行只加载 Actor。第一版用 MLP 与显式时序特征，不使用图像端到端网络、循环网络、多智能体 RL 或在线自我更新。

比赛策略奖励以终场规则得分差为主。训练期间可加入经消融验证的稀疏进度奖励，避免策略只追求即时小分：

```text
R = 版本化裁判计分器给出的终场分差
    - λr × 重试时间与无效任务代价
    + 经消融验证的 Φ(状态变化) - γ × Φ(前一状态)
```

硬规则违规由环境状态机阻止或按 V3 规则转成强制重试/取消资格事件，不以调大软惩罚代替规则建模。`Φ` 只用于引导训练，不改变正式规则计分；五色石分值以及分值是否包含运输分必须由裁定版本的记分器确定，未裁定期间不得调奖励系数“猜规则”。训练记录真实终场总分与规则平局指标、任务完成率、空跑时间、碰撞、重试、违规、失误物品和终场持物，不能只看训练 reward。

本期不训练局部导航策略。未来若启动，应另建任务级局部基准，奖励安全到达/恢复成功，统计碰撞、塔接触、区域越界和恢复时长；规则禁止的动作在环境与安全层直接屏蔽，而不是仅做软惩罚。

## 6. 训练环境与数据

### 6.1 快速比赛环境

新建 Python/Gymnasium 比赛环境，以 `config/field_geometry.yaml` 为场地几何输入，以明确版本的规则解析和记分器为规则输入，使用简化的离散事件模型完成 180 秒一局。环境包含 TR/BR 区域角色、用品状态与最多持物数、转运事件、建塔合法性与结构、塔顶翻转与归属、保护法则锁存、五色石交接/放置、重试和强制等待、失误/犯规、终场停止与计分核查。对 V3 文件冲突做可配置分支并阻止默认训练启动，直到选择经书面裁定的规则配置。

随机化内容包括出生位/初始资源、对手策略、共享区占用与阻塞时长、对手翻塔或争球动作、动作执行延迟、路径通行时间、感知漏检/误检/过期和里程计误差。训练时策略只看到带噪声且有置信度/年龄的观测；环境真值只供奖励和评估，不能混入 actor 输入。每局记录固定 seed、规则版本、策略版本和事件轨迹，便于复现。

### 6.2 Gazebo 的用途

继续使用现有 Gazebo 场地和传感器链做定位、路段、停车距离、窄口会车与局部避让的闭环验证。后续补充机器人运动控制、对手/障碍模型和可触发比赛事件。Gazebo 传感器真值可用于仿真评估，但策略仍只订阅与实机一致的结构化状态接口。

### 6.3 MuJoCo 的用途

使用现有 `rl` 环境（Python 3.11、MuJoCo 3.15、Gymnasium 1.4、PyTorch 2.11 CUDA）建立可复现的机器人动力学与操作验证模型。仓库目前没有现成 MJCF，因此首个工程产物应是从场地 YAML 生成静态场地、并绑定真实机器人 CAD/质量/关节限位的 MJCF，而不是直接训练策略。先验证双侧夹持塔基/中段、塔顶垂直抓放与原塔翻转、建塔误差容限、纸箱接触/滑落、层间运动、急停/失控保护等关键事件；用实测动作时间、滑移率和定位误差校准模型。

快速规则环境负责 180 秒比赛级任务和奖励，适合并行 rollout 与大量 PPO 训练；MuJoCo 负责动力学、夹持、摆放精度与塔体稳定性，可用于控制器/操作原语验证，之后才判断是否值得用于局部策略训练；Gazebo 负责现有 ROS 传感器、定位和通信链的闭环验证；rosbag 回放负责状态接口、决策重放和退化场景回归。四者共享由 `field_geometry.yaml` 派生的地图与版本化规则/状态契约，但分工不同，不要求每次比赛策略 rollout 都跑 MuJoCo。

## 7. 基线、验证与放行门槛

先建立可复现的确定性基线：当前任务规则/贪心策略加同一套路网执行器。每次比较让基线与 RL 使用相同场景 seed、对手、资源和传感器扰动。训练集、验证集和最终测试集按 seed/场景族分离，避免同一类场景泄漏。

建议分级验收：

1. **环境正确性**：规则单测覆盖计分、资源、重试、区域权限和终场行为；随机对局中无非法状态转移；关键比赛事件与规则样例逐条对齐。
2. **策略评估**：在至少 500 个未参与训练的随机对局上与基线成对比较。平均最终分差需有统计显著改善，或在分数不降时显著降低失败/重试；违规、撞塔和区域越界必须为零（按正确环境模型），终场持物不高于基线。报告均值、分位数、置信区间、种子和规则版本，并按场景分组。
3. **确定性导航闭环**：覆盖静态/动态阻挡、公共区会车、定位降级、控制延迟、地面-L1坡道/阶梯及规则最终确认后的 L1-L2 结构；危险动作必须被安全过滤器拒绝。
4. **影子模式**：实机运行策略但不执行其建议，与实际人工/基线动作及赛后结果对照；检查动作合法率、状态新鲜度、推理时延和基线差异。
5. **限权闭环**：先在影子模式记录上层任务建议；随后只开放低风险任务选择，任务落地仍由确定性状态机执行。赛前保存已验收模型并可一键切回确定性任务基线；比赛中不在线训练。

模型版本必须绑定状态 schema、动作 schema、规则版本和场地配置哈希。接口不匹配、NaN、超时、无合法动作或置信度不足时，策略节点拒绝输出并报告原因。

## 8. 安全边界

- 安全过滤器按当前所在区域、速度、路段、持握数、比赛阶段及状态有效性过滤候选动作。
- 底盘急停、驱动限速、碰撞保护、终场释放和主机失联兜底在 STM32/确定性执行层独立运行。
- 策略只能请求已登记的任务/路段/动作原语，不得发布任意电机命令，不得修改规则参数或安全阈值。
- 定位不可靠、障碍状态过期或关键建筑位未知时，禁止依赖这些信息的高风险动作；策略可选择等待、重定位或安全回退。
- 策略服务进程独立于感知和串口关键路径。策略节点崩溃不得拖垮感知、通信或急停。

## 9. 实施顺序

### Phase 0：冻结接口与规则事实

整理策略输入字段的来源、有效位、观测年龄、动作合法条件；向组委会确认 V3 内部冲突、对手区域/场地尺寸，并冻结记分器规则版本和资源/交接状态来源。定义版本化 `DecisionState`、`CandidateAction`、`PolicyAction` 和执行结果消息/接口。当前 `PerceptionFrame` 中的占位字段不可未经有效位检查直接作为真值。Phase 0 的完成条件是：每个输入字段都有权威来源、单位、坐标系、有效位/年龄和缺失时回退动作；没有来源的资源、持握、队伍颜色字段不得进入训练观测；分值冲突解决前不得进行正式 reward 训练。

### Phase 1：确定性基线与比赛环境

实现 V3 版本化规则状态转移、记分器和确定性 baseline；完成 Gymnasium 环境、随机场景生成、记录与回放、成对评估工具。用手算对局核实搬运分与建塔分不重复、塔顶归属、平局顺序、重试罚时及终场快照。规则裁定前只做环境单测，不训练五色石相关策略。

### Phase 2：比赛策略 Maskable PPO

在书面裁定规则版本及其场景模型后，使用 SB3 Contrib Maskable PPO 训练上层任务分配策略，覆盖取物、交接、建塔、塔顶归属、共享区风险、可选的五色石流程、任务切换和终场收尾。策略输出候选任务，不直接控制导航。与 baseline 完成离线成对对局、规则平局比较和未见 seed 评估后，冻结 actor。

### Phase 3：MuJoCo 操作验证与确定性路网

从 YAML 生成场地静态几何，建立真实机器人 MJCF；验证夹持/放置/翻顶等动作原语与塔稳定性。同时实现经过场地验证的路网、路径跟踪器和确定性等待/备选边/恢复机制；分层关系以最终实场几何为准。该阶段不训练局部 PPO。只有在确定性基线存在已量化的问题、且能建立可靠闭环验证集时，另立局部 RL 阶段与验收门槛。

### Phase 4：ONNX 推理和影子运行

加入独立 `decision_policy_node` 与 ONNX actor 加载、Actor schema 校验、规则动作掩码、安全过滤、超时和确定性基线回退。先做 rosbag 重放和影子模式，测 CPU 占用、推理时延、状态更新到动作生效的总时延及降级表现。

### Phase 5：Gazebo 闭环与限权实机

Gazebo 验证确定性通行、任务切换与安全恢复；通过后在低风险上层任务集合下实机闭环。每次只开放一类新任务建议，持续保留基线回退与实体急停。只有策略在目标场景上稳定胜过基线且没有规则/安全事件，才扩大候选任务集合。

## 10. 主要风险与处理

| 风险 | 影响 | 处理 |
|---|---|---|
| 快速环境与真实比赛差异 | 学到仿真特化策略 | 随机场景、对手多样化、Gazebo闭环、影子模式及实测回放 |
| 感知不确定性被策略误当事实 | 错误抢占/建造/碰撞 | 将有效位、置信度、年龄纳入状态；高风险动作由安全层屏蔽 |
| 奖励投机或只追局部得分 | 终场成绩下降、违规增多 | 以规则终场得分为主，单独报告硬指标，成对比较 baseline |
| 路网候选动作不足 | 被挡住时没有可选行为 | 先检查关键区域备选边和安全等待点；不可达时明确上报上层换任务 |
| 推理争用 CPU | 感知/控制延迟上升 | 小型 MLP、低频推理、独立节点、实际平台压力测试与超时回退 |
| 训练环境规则不完整 | 模型优化错误目标 | 规则事实测试先于训练；未裁定规则采用保守动作屏蔽，不在奖励里猜测 |

## 11. 本方案明确不纳入的内容

- 不做相机图像到动作的端到端 RL；视觉 DL 继续负责检测/分类，策略只消费结构化状态。
- 不训练策略输出电机 PWM、轮速或自由形式轨迹。
- 不在实机比赛中在线更新模型。
- 不引入多智能体 RL 作为首版；对手以多种规则化策略和随机行为建模。
- 不把已有 Gazebo 巡游当作完整比赛训练环境。
