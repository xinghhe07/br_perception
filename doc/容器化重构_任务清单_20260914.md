## 〇、给执行者的总则（**每个任务开始前都要看**）

### 红线 —— 不许碰

| 项 | 原因 |
|---|---|
| `config/field_geometry.yaml` 的几何数据 | **场地唯一事实源**，经过 SolidWorks 线稿实测 + 逐条人工确认。重构只改代码，不改场地数据 |
| `scripts/field_model_generator.py` | 它的 `--apply` **会直接覆写** `config/field_geometry.yaml`，冲掉上述回填结果。**不要运行** |

### 已知坑（踩过的，别再踩）

1. **QoS 兼容性** —— 2026-09-14 全仓库修过一轮。规则：
   - **订阅端一律 `rclcpp::SensorDataQoS()`**（BEST_EFFORT）。RELIABLE 订阅 ↔ BEST_EFFORT 发布 = 静默收不到数据，且**不报错**。
   - **发布端保持 `SystemDefaultsQoS()` / RELIABLE 不动** —— RELIABLE 发布对两种订阅者都兼容；改成 BEST_EFFORT 反而会踢掉别人的 RELIABLE 订阅（Point-LIO 可能就是）。
   - 出现"话题在、节点在、就是没数据"，**第一个怀疑 QoS**。
2. **仿真雷达垂直 FOV = ±14.9°**，与实机 Mid-360 的 −7°~+52° 不同。桥接节点 `pointcloud2_to_livox_custom` 的 `elev_min_deg`/`elev_max_deg` 已按仿真值配置，别照搬实机参数。
3. **Gazebo 改模型后必须整个重启**，不热重载。
4. **仿真雷达实际发布率 ~33Hz**（SDF 里的 `update_rate: 10` 对 CPU `ray` 不生效），实机 10Hz。
5. **本仓库是"仓库根 = ROS 包"**（`CMakeLists.txt` / `package.xml` 在根目录），不是 `src/<pkg>` 结构。
6. Ubuntu 上**只有 `python3`，没有 `python`**。

### 两条实现并存的事实（本次重构要解决的核心）

- 单体 `src/lidar/lidar_perception_node.cpp`（1570 行）**自己实现了全套算法**，没有 include 任何子模块头
- 5 个组件（`lidar_preprocessor` / `ground_segmenter` / `cylinder_detector` / `cluster_extractor` / `building_spot_analyzer`）是**同一套代码的另一份**，都是 `rclcpp::Node` 子类，且**没有任何 launch 启动它们**
- 两边**重复发布同名话题**，QoS 还不一样
- 组件的 `GroundSegmenter::validate_plane_normal` / `refine_inliers_adaptive` / `classify_by_platform` / `normalize_coefficients` 与单体内 869–935 行**同名同逻辑** —— 确认是复制，不是两套演化

   ```cpp
   namespace br_perception::lidar {
   using CloudPtr = pcl::PointCloud<pcl::PointXYZI>::Ptr;
   class LidarPreprocessor {
   public:
     struct Params {
       double leaf_size{0.05};
       bool   enable_outlier_filter{true};
       int    outlier_mean_k{10};
       double outlier_std_thresh{1.0};
       double roi_min_x{-10.0}, roi_max_x{30.0};
   ```
