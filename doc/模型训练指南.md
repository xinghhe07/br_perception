## 1. 训练尺寸：和推理保持一致

### 为什么不直接用 640×640

相机是宽幅（16:9 或 4:3），而 640×640 是正方形。用 Ultralytics 默认的 letterbox
塞进 640×640，会**上下留大片黑边**——16:9 的画面缩到 640×360，上下各补 140px，
**画布 44% 是纯零填充**。你们要检测的 200mm 天空方块、Ø180 柱顶凹槽本来就小，
等于白扔一半像素。

### 推荐：训练和推理都用 640×384（或按相机比例算出的最接近值）

| 相机 | 等比缩放后内容区 | 补到 32 的倍数 | 训练/推理尺寸 |
|---|---|---|---|
| 1280×720 (16:9) | 640×360 | 640×384 | **640×384** |
| 1920×1080 (16:9) | 640×360 | 640×384 | **640×384** |
| 1440×1080 (4:3) | 640×480 | 640×480 | **640×480** |
| 1280×960 (4:3) | 640×480 | 640×480 | **640×480** |

**规则**：`内容高度 = 640 ÷ 宽高比`，然后**向上取到 32 的倍数**。

> YOLO 是全卷积网络，**推理尺寸不必等于训练尺寸**，只要是 32 的倍数。
> 但**训练和推理用同一个尺寸最省心**——省掉所有坐标换算的心智负担。

### 训练命令（以 640×384 为例）

```bash
pip install ultralytics

yolo detect train \
  model=yolo26n.pt \
  data=br_objects.yaml \
  imgsz=384 \          # 注意: 这里给的是【高度】; 宽度走 rect
  rect=True \          # 矩形训练 —— 关键, 否则会 pad 成正方形
  epochs=200 \
  batch=16 \
  device=cpu           # 有 GPU 的机器上训练, 部署到 CPU

# 导出 ONNX (opset 12+; 动态轴便于换分辨率)
yolo export model=runs/detect/train/weights/best.pt format=onnx imgsz=384,640 opset=12
```

> ⚠️ `imgsz` 的确切写法随 Ultralytics 版本变（单数=正方形，元组=`(h,w)`）。
> **跑 `yolo cfg` 或查当前版本的文档确认一遍**，别照抄。

## 2. 类别定义

### 只有这两个走 YOLO

`mustika_detector` / `pillar_detector` / `building_spot_detector` **已经用纯 HSV 实现了**，
不走神经网络。只有这两个需要训练：

| 类别 | 规则书尺寸 | 说明 |
|---|---|---|
| `earth_block` | 350×350×350mm | 地球方块，红/蓝两队各 20 个 |
| `sky_block` | 200×200×200mm | 天空方块，**红蓝双面**，共 12 个 |

### 颜色不交给网络

v1.7 §3.2/§3.3 定的是 **"YOLO 定位 + HSV 判色"**：

```
YOLO 只负责: "这里有个方块"（bbox）
HSV 后处理:  "它是红的还是蓝的"（在 bbox 内统计）
```

**所以类别里不要拆 `earth_block_red` / `earth_block_blue`** —— 红蓝交给 HSV，
网络只管"是不是方块"。这样训练数据量小、泛化好，而且**光照变了只调 HSV 阈值，不用重训**。

> `sky_block` 的特殊之处：**顶面颜色决定得分**（规则 3.5.6）。所以推理时除了 bbox，
> 还要确定"哪个面是顶面"——靠 bbox 的几何 + 透视估计，不是靠网络。

## 3. 数据集

### 规模
- **每个类别 ≥ 500 张**，其中要有相当比例是**小目标**（远处、俯视）
- 训练集:验证集 ≈ 8:2

### 采集要求（按比赛现场还原）
1. **光照要覆盖赛场最坏情况** —— 场馆顶部射灯造成的过曝、背光、阴影。
   （检索到的同类赛事案例：有 985 队伍因现场光照识别率**跌破 40%**）
2. **多角度、多距离** —— 远景/近景各占一半，别全是近景清晰图
3. **要有遮挡样本** —— 方块被机器人夹爪挡住一半、被其它方块挡住
4. **背景要有干扰** —— 场地地面颜色、绿色建筑位、棕色柱、围栏

### 标注
- bbox 紧贴目标外沿，**不要留边距**（留边距会让 HSV 判色区混进背景）
- 被遮挡 >70% 的目标**不标**，30–70% 标注并保证可见部分完整
- 用 LabelImg / CVAT / Roboflow 都行

## 4. 训练/推理的一致性检查（最容易翻车的一步）

**训练和推理的预处理必须逐位一致**，否则模型看到的分布和学到的不一样。

| 项 | 训练时 | 推理时必须一致 |
|---|---|---|
| 缩放方式 | Ultralytics 的 **letterbox**（等比 + 补边） | ❌ 你们的 `image_preprocessor` 现在是**硬 resize**（无补边） |
| 输入尺寸 | 640×384 | config `model_input_w/h` |
| 归一化 | 0–255 → **0–1（只除以 255）** | ❌ 现在错：见下面「归一化怎么改」 |
| 通道顺序 | RGB | `pixel_format` |
| 补边值 | 114（Ultralytics 默认灰） | ⚠️ 改成 letterbox 后必须也是 114，**不是 0 黑** |

> ⚠️ **当前代码错在哪（精确版）**：
> `src/camera/image_preprocessor.cpp:412` 是纯 `cv::resize`，**等比缩放到 640×384，没有补边**。
> 而相机 1280×720 是 16:9、640×384 是 5:3 →
> **纵向被拉伸 6.7%**（360 被拉到 384）。
>
> （之前口算的 78% 是"若直接拉伸到 640×640"的数 —— 当前配置是 640×384，**实际形变是 6.7%**。）
>
> 6.7% 不算致命，但它**精确地打在几何判据上**：`min_angle_score`(直角)、`min_side_score`(边长)、
> `min_aspect_ratio`(长宽比)、`min_circularity`(圆形度) 全都会被推偏。
> 改成 letterbox 后这些判据的阈值才谈得上"按真实形状标定"。

### 归一化怎么改 —— 一行配置的事

`src/camera/image_preprocessor.cpp:429` 的 `apply_normalization` 做的是 **ImageNet 归一化**：

```cpp
rgb.convertTo(rgb_float, CV_32FC3, 1.0/255.0);   // → [0,1]
cv::subtract(rgb_float, Scalar(mean[0..2]), normalized);
cv::divide(normalized,  Scalar(std[0..2]),  normalized);   // (x-mean)/std
```

**而 Ultralytics 导出的 ONNX 只接受 0–1 的 float32，不做 ImageNet 归一化。**

当前配置是 `enable_normalize: false` → **归一化整段跳过，直接喂 0–255** —— 分布差了 255 倍，
模型基本等于瞎猜。

**修法：不用改代码，改配置就行**（让现有公式退化成"只除 255"）：

```yaml
# config/camera_params.yaml → image_preprocessor
enable_normalize: true          # 打开
norm_mean: [0.0, 0.0, 0.0]      # 不减均值
norm_std:  [1.0, 1.0, 1.0]      # 不除标准差
```
→ `(像素/255 − 0) / 1` = **0–1 float32** ✅

**已核实（`preprocess()` 的真实分支）：**

```cpp
if (normalize_enabled) { ... out_encoding = TYPE_32FC3; }   // float32
else                   { ... out_encoding = RGB8; }          // ← uint8, 0–255
```

**`enable_normalize: false` → 输出 uint8、0–255。ONNX Runtime 要 float32、0–1。**

→ **类型不对 + 量程差 255 倍。当前配置下 YOLO 通路根本跑不起来，换什么模型都一样。**

---

### 第三个不一致：CLAHE 和曝光补偿

`preprocess()` 里这两步是**无条件执行**的：

```cpp
if (clahe_enabled) working = apply_clahe(...);   // 默认 true
working = compensate_exposure(working);          // ← 无条件，V 通道直方图拉伸
```

**Ultralytics 训练时不做这两步。** 也就是说推理喂给网络的图像，
**对比度和亮度分布和训练时完全不同** —— 又一个训练/推理分布错配。

**二选一：**
- (a) **推理侧关掉** —— `front/rear_clahe_enabled: false`，并把 `compensate_exposure` 改成可配置关闭
- (b) **训练侧也做** —— 用同一套 CLAHE+曝光补偿预处理**生成训练集**（推荐，因为赛场光照突变确实需要它，v1.7 §3.1 就是为这个加的）

> (b) 更符合 v1.7 的意图，但要求**训练数据必须过同一套预处理**——
> 不能拿原始图训、拿增强图推。

### 反投影：别忘了把框算回原图

letterbox 之后，检测框的坐标是**缩放+填充后**的。要 2D→3D 投影，必须反算：

```
x_orig = (x_letterbox - pad_x) / scale
y_orig = (y_letterbox - pad_y) / scale
```

**这一步不做，所有投影全偏**，而且偏得很隐蔽（近处看不出来，远处错得离谱）。

## 7. 一句话总结

1. **先量相机** —— 不知道真实分辨率和宽高比，后面全是猜
2. **训练尺寸 = 推理尺寸**，取 `640 ÷ 宽高比` 后向上对齐 32
3. **类别只留 `earth_block` / `sky_block`**，红蓝交给 HSV
4. **letterbox，不是 resize** —— 这是当前代码最要命的错
5. **反投影要反算**，不然 2D→3D 全偏
6. **上机前实测推理延迟**，旧基线不能用了
